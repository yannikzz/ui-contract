# 结构规范 layout.md

> **给编码 agent 的三句话：**
> 1. 改动任何界面结构之前，走一遍 §1 落位决策树。落位了就直接实现，不需要改本文档。
> 2. 没落位就**停**。不要自己新开区域、新开 tab、新开浮层。走 §9 变更流程。
> 3. 代码里出现的每一个区域标记都必须在 §2 白名单里。表里没有的名字就是违规。

适用产品：React Native 记账 app（iOS + Android，竖屏为主）。
配套文件见 `docs/ui-contract/config.md` 路径表。

---

## §0 与视觉规范的分工

**唯一的切线**：换一套品牌皮肤时它会变吗？会变 → `design.md`；不会变 → 本文档。

| 事项 | 归属 | 为什么 |
|---|---|---|
| 区域树、区域名白名单 | 结构规范 | 换皮肤不动 |
| 页型、区域出现与否 | 结构规范 | 换皮肤不动 |
| tab 数量上限、栈深上限 | 结构规范 | 是结构参数 |
| 折叠顺序、折叠后必须留下什么 | 结构规范 | 换皮肤不动 |
| 颜色、字号、圆角、阴影 | 视觉规范（值在 token 文件） | 换皮肤全变 |
| 间距刻度（8/12/16…） | 视觉规范 | 换皮肤会变 |
| 「两个区域之间必须有间隔」这条规则本身 | 结构规范 | 间隔多大是视觉的，有没有间隔是结构的 |
| 「超支」标记的**颜色和形状** | 视觉规范 | 换皮肤会变 |
| 「超支」标记**出现在哪个区域**、能不能是数字 | 结构规范 | 见 §7 |
| 列表条目的内边距 | 视觉规范 | |
| 列表条目里**不能有按钮** | 结构规范 | 见 §6 |

**硬规则**

- 本文档不含任何颜色值、字号值、圆角值、间距值。需要值的地方写「见 `design.md` §X」。**结构参数除外**：区域数量、tab 上限、栈深、每屏滚动容器数量、以「能显示几个条目」表达的最小可用高度阈值。
- `design.md` 不含区域树、区域名、页型定义。
- **既有代码不是权威。** 代码和本文档冲突时，改代码。

⚠ **唯一的耦合点**：`screen.summary` 是定高非滚动区（本文档 §2、§3）。它能不能一行放下当期三个数字，取决于 `design.md` 定的字号与无障碍放大策略。**改这两处任何一处，都要回头看另一处。** `design.md` 侧必须标同样一条。

## §1 落位决策树

拿到一个新的界面需求，从这里进入。终点要么是一个具体区域名，要么是「停」。

### 一、短路（先看这五条，命中就结束）

| # | 判断 | 落位 |
|---|---|---|
| **S1** | 这是「东西长什么样」（颜色/字号/圆角/图标风格/动画时长）吗？ | 不归本文档，见 `design.md` |
| **S2** | 这是一个输入/选择的过程吗？ | **多个字段、要产出或修改一个一等对象** → `overlay.body`（提交按钮进 `overlay.action-bar`）<br>**只选一个值、选完立刻返回调用方** → `sheet.body` |
| **S3** | 这是用来改变「当前这屏在看什么范围」的控件吗（时间区间、分类筛选、排序、搜索）？ | `screen.filter-bar` |
| **S4** | 这是一个**配置项**吗——一个可以被设成某个值、并且被记住的开关或选项，用户一个月碰不到一次？ | 设置层，即 `settings-list` 页型的 `screen.body` |
| **S5** | 这是**提示**而不是内容吗？ | **关于当前这屏数据可不可信**（同步失败、离线、数据不全）→ `screen.notice`<br>**关于导航里某个去处有状态变化** → `tab-bar`，且必须服从 §7 徽标规则 |

> **S4 只管配置项，不管动作。** 「导出全部账单」「批量导入」「联系作者」是动作，不是配置项，S4 **不**接它们——它们走主干，并且会走到「停」。这是故意的：本产品目前没有全局动作的容身处，把它们塞进设置正是本文档要阻止的事。

### 二、主干

短路都没命中，从这里走。每个叶子都是一个具体区域名，或者「停」。

```
Q_A 它是某个一等对象（交易 / 账本 / 预算 / 分类，见 §5）的一个切面吗？
 ├─ 是 ─→ Q_B 它自己就是一屏，还是已有一屏里的一段？
 │        ├─ 自己就是一屏 ────────────→ detail 页型的 screen.body（新增类型要走 §5 准入）
 │        └─ 已有屏里的一段/已有条目上的一个字段 → 那一屏的 screen.body
 │
 └─ 否 ─→ Q_C 它是对当前这屏整份数据的聚合数字吗？
          ├─ 是 ─→ Q_D 它定高、无交互、一眼看完吗？
          │        ├─ 是 ──────────────────→ screen.summary
          │        └─ 否（图表 / 可展开 / 高度随数据变）→ screen.body
          │
          └─ 否 ─→ Q_E 它是一个用户主动触发的动作吗？
                   ├─ 是 ─→ Q_F 它作用于当前这屏正在看的那个对象吗？
                   │        ├─ 是 ──→ detail 页型：screen.action-bar
                   │        │         overlay 内：overlay.action-bar
                   │        └─ 否，它作用于全局或整份数据 ──→ 【停 → §9】
                   │
                   └─ 否 ─→ Q_G 它是一个新的常驻去处吗（用户会主动想去看的一类内容）？
                            ├─ 是 ──→ 【停 → §9】（新增 tab 走 §7 导航准入）
                            └─ 否 ──→ 【停 → §9】
```

### 三、什么都没命中

**停。** 不要挑一个最像的区域塞进去，不要新开区域、tab、浮层，不要「先放设置里」。走 §9 提一份区域申请。

**兜底永远是「停」，不是任何一个真实区域。** 一旦某个真实区域成为兜底，它就会变成垃圾抽屉——那正是写这份文档要防的事。「停」是叶子：它离开本文档去走变更流程，不会绕回决策树。

### 四、反向检查清单

你如果正准备做下面任何一件事，说明你已经走偏了，回到 §1 重走：

1. 新开一个 tab
2. 让 overlay 再开一个 overlay，或者在 sheet 上再叠一个 sheet
3. 在流水条目里塞一个可见按钮
4. 往 `screen.summary` 里放可点击、可滚动、或者高度会变的东西
5. 因为「暂时不知道放哪」，先放进设置层
6. 在一屏里建第二个滚动容器

### 五、验证记录（对抗性输入 + 日常输入）

| 输入 | 落点 |
|---|---|
| 「导出全部账单为 CSV」——不属于任何对象的一次性动作 | S1–S5 均不命中（S4 只管配置项）→ Q_A 否 → Q_C 否 → Q_E 是 → Q_F 否（作用于整份数据）→ **停 → §9** ✓ |
| 「本月预算剩余 ¥800」——看起来两个区域都行 | Q_A 否 → Q_C 是 → Q_D 是（定高、无交互）→ `screen.summary`。若做成每个分类一个进度条的列表，则 Q_D 否 → `screen.body`。Q_D 就是那个判定问题 ✓ |
| 「加一个『账户』tab」——撞上限 | Q_A 否（账户不在 §5 一等对象里）→ Q_C 否 → Q_E 否 → Q_G 是 → **停 → §9**，并受 §7 库 tab 上限 4 约束 ✓ |
| 「流水页顶部放一条促销 banner」——根本不该有 | S5 不命中（与数据可信度无关）→ Q_A/C/E/G 全否 → **停 → §9** ✓ |
| 「流水条目上显示备注」 | Q_A 是 → Q_B 已有条目上的一个字段 → `screen.body` ✓ |
| 「统计页加一个按分类占比的环形图」 | Q_A 否（统计是视图不是对象）→ Q_C 是 → Q_D 否 → `screen.body` ✓ |
| 「明细页加『只看支出』切换」 | S3 → `screen.filter-bar` ✓ |
| 「记一笔时选分类」 | S2 单值选完即返回 → `sheet.body` ✓ |
| 「预算超支时在预算 tab 上提示」 | S5 导航状态提示 → `tab-bar`，按 §7 只能是状态点不能是数字 ✓ |

## §2 区域名白名单

> **本表有三种形式，改一个就必须改另外两个**：本表 / `src/ui-contract/regions.ts` 的 `RegionId` 联合类型 / 同文件的 `REGION_META` 元数据。
> **同步顺序固定：本表 → 类型 → 代码，不可反向**（理由见 §9）。

**命名约定**：全小写 kebab-case；嵌套用 `.` 分隔；**最大深度 2**。文档里的名字、`RegionId` 类型里的名字、代码里 `<Region id="...">` 的名字，三处必须逐字相同。

### app 层（跨屏常驻，不属于任何一屏）

| 区域名 | 职责（一句话） | 允许放 | **禁止放** | 尺寸约束 |
|---|---|---|---|---|
| `app-root` | 整个 app 的根容器 | 恰好一个导航器 + `overlay-host` + `sheet-host` | 任何业务内容、任何直接可见的 UI | — |
| `tab-bar` | 底部主导航 | 库 tab 项、恰好 1 个动作槽、§7 允许的状态点 | 业务数据、金额、库 tab 上的数字徽标、第 2 个动作槽 | 库 tab 上限 4，动作槽恰好 1 |
| `overlay-host` | 全屏覆盖层的挂载点 | 同时最多 1 个 overlay | 第 2 层 overlay、任何常驻内容 | 最大 1 层 |
| `sheet-host` | 底部弹层的挂载点 | 同时最多 1 个 sheet | 第 2 层 sheet、多步流程 | 最大 1 层 |

### 屏内层（每一屏一棵树，不是全 app 一棵树）

| 区域名 | 职责（一句话） | 允许放 | **禁止放** | 尺寸约束 |
|---|---|---|---|---|
| `screen.header` | 当前屏是什么、怎么离开 | 标题、返回、账本切换入口、设置层入口 | 主要动作、筛选控件、金额数字 | 单行，不滚动 |
| `screen.notice` | 当前屏的数据可不可信 | 降级/失败/离线说明 + 一个重试 | 营销、引导、成功提示、会自动消失的东西 | 不滚动，无内容时高度为 0 |
| `screen.filter-bar` | 当前屏在看哪个范围 | 时间区间、分类筛选、排序、搜索入口 | 产生新数据的动作、导航到别屏的入口 | 单行，不滚动 |
| `screen.summary` | 当前范围的聚合数字 | 定高、无交互、一眼看完的数字 | 图表、可展开内容、按钮、任何高度随数据变的东西 | 定高，不滚动，最多 3 个数字 |
| `screen.body` | 当前屏的全部内容 | 列表、图表卡片、详情段落、空/加载/失败态 | 第 2 个滚动容器、常驻在视口内不随滚动移动的东西 | **每屏恰好 1 个**，唯一的滚动容器 |
| `screen.action-bar` | 作用于本屏那个对象的动作 | 保存、删除、编辑等作用于当前对象的按钮 | 导航、筛选、作用于全局的动作 | 不滚动；**只在 detail 页型出现** |

### 浮层内层

| 区域名 | 职责（一句话） | 允许放 | **禁止放** | 尺寸约束 |
|---|---|---|---|---|
| `overlay.header` | 这个流程是什么、怎么放弃 | 标题、取消 | 提交按钮、筛选 | 单行，不滚动 |
| `overlay.body` | 流程的输入内容 | 表单字段、分步内容、字段级错误 | 导航到别屏的入口、第 2 个滚动容器 | 恰好 1 个滚动容器 |
| `overlay.action-bar` | 提交这个流程 | 提交/下一步 | 取消（在 header）、删除、导航 | 不滚动；键盘弹起时必须跟随上移 |
| `sheet.header` | 在选什么 | 标题、关闭 | 提交、筛选 | 单行，不滚动 |
| `sheet.body` | 可选的值 | 单一用途的选项列表/选择器 | 多步流程、导航到第三屏、表单 | 恰好 1 个滚动容器 |
| `sheet.action-bar` | 确认选择（仅多选时需要） | 确认 | 删除、导航、提交整个流程 | 不滚动；单选 sheet 不应出现此区域 |

> **本表的代码形式**：`src/ui-contract/regions.ts` 里的 `RegionId` 联合类型 + `REGIONS` 元数据。
> **改本表就必须同步改那两处，顺序见 §9：白名单 → 类型 → 代码，不可反向。**

## §3 外壳骨架

### 区域树

```
app-root                          ← 固定，全屏
├── navigator                     ← 弹性，占满 tab-bar 以上
│   └── <当前屏>                   ← 每屏一棵树，见下
│       ├── screen.header         ← 固定单行
│       ├── screen.notice         ← 固定；无内容时高度 0
│       ├── screen.filter-bar     ← 固定单行；部分页型没有
│       ├── screen.summary        ← 固定高；部分页型没有
│       ├── screen.body           ← 弹性，吃掉剩余全部高度，唯一滚动容器
│       └── screen.action-bar     ← 固定；仅 detail 页型
├── tab-bar                       ← 固定；detail / overlay 下隐藏
├── overlay-host                  ← 正交层，最多 1 层
│   └── overlay.header / overlay.body / overlay.action-bar
└── sheet-host                    ← 正交层，最多 1 层
    └── sheet.header / sheet.body / sheet.action-bar
```

### 图上看不出来、但决定扩展规则的四件事

1. **`tab-bar` 属于 app 层，不属于任何一屏。** 所以 push 一个 detail 屏时是导航器把它藏起来，屏自己**不能**画一个假的 tab-bar 出来——那会造成两个真相源，返回时闪烁。
2. **`overlay-host` 和 `sheet-host` 与整棵屏树正交**，不是任何一屏的子节点。所以 overlay 打开时，下面那屏的滚动位置、筛选状态、加载中的请求**必须原样保留**，关闭后原样恢复。这条不成立的话，「记一笔」就会把用户的浏览位置冲掉。
3. **每屏恰好一个滚动容器，就是 `screen.body`。** header / notice / filter-bar / summary / action-bar 全部不滚动。这条直接决定了：新增一块内容几乎总是加进 `screen.body`，而不是新开一条常驻带。想加常驻带就是在改外壳，走 §9。
4. **`screen.summary` 定高。** 所以任何高度随数据变化的东西都不能进去，哪怕它确实是个「汇总」——分类汇总列表、环形图都归 `screen.body`。

### 降级

**触发条件**是「`screen.body` 的可用高度装不下 3 个完整列表条目」，不是某个具体屏幕宽度。用真实测量值判断，不要写死断点——断点不知道 filter-bar 有没有折叠，会做多余的折叠。

真实触发场景按发生频率排：无障碍大字号 > 键盘弹起 > 小屏机型 > 横屏。

**折叠顺序**（依次执行，每折一步重新测量）：

1. `screen.summary` 折成单行
2. `screen.filter-bar` 折成一个入口按钮，点开是 sheet
3. `screen.notice` 折成一个图标 + 一行
4. **`screen.body` 和 `screen.action-bar` 永不折叠**

**折叠后必须留下的信号**（信号条）：

- `screen.summary` 折叠后必须留下**当期结余那一个数**。三个数留一个，不能留零个——留零个的话用户失去了「这个月还剩多少」这个唯一的高频信息。
- `screen.filter-bar` 折叠后必须留下**当前范围的文字**（如「2026 年 8 月」）。这是折叠时最容易丢的信号：丢了以后用户不知道自己在看哪个月，会把筛选后的空结果误读成数据没了。

**键盘弹起时**：`overlay.action-bar` 必须跟随键盘上移并保持可见（否则记一笔时看不到提交按钮），`tab-bar` 隐藏。

**手动 vs 自动，谁赢**：**用户赢，两个方向都是。** 用户手动折起来的，空间回来了也保持折叠；用户手动展开的，即使触发了降级条件也保持展开（此时允许 `screen.body` 变矮）。自动降级是兜底，不是意见。

### 上下文形态

本产品有一个层级：**账本 → 交易**。

- **账本**是划分单位：同一时刻恰好有一个「当前账本」，`screen.summary`、`screen.filter-bar`、统计、预算**全部只作用于当前账本**。
- 切换账本从 `screen.header` 的账本切换入口进入，形式是 sheet。
- **「账本」和「分类」不是一回事，不要混。** 账本是容器（交易属于且只属于一个账本，跨账本不聚合）；分类是标签（用于聚合，一笔交易在账本内被分类）。两者都是一等对象，但账本决定「算不算进来」，分类决定「算进哪一堆」。

## §4 页型

| 页型 | 结构 | 用于 | 判别特征 |
|---|---|---|---|
| `tab-root` | header + notice + filter-bar + summary + body | 明细、统计、预算 | tab-bar 可见；无 action-bar；永不清空 |
| `detail` | header + notice + body + action-bar | 一笔交易、一个预算、一个分类、一个账本 | tab-bar 隐藏；恰好承载一个一等对象 |
| `editor` | overlay.header + overlay.body + overlay.action-bar | 记一笔、编辑一笔、编辑预算 | 挂在 overlay-host 上；完成后回到原处，不改导航栈 |
| `settings-list` | header + body | 设置及其子页 | 无 filter-bar、无 summary、无 action-bar；固定目录，不随数据增减 |

### 页型 × 外壳部件矩阵

| | `tab-bar` | `screen.header` | `screen.notice` | `screen.filter-bar` | `screen.summary` | `screen.body` | `screen.action-bar` |
|---|---|---|---|---|---|---|---|
| `tab-root` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ |
| `detail` | ✗ | ✓ | ✓ | ✗ | ✗ | ✓ | ✓ |
| `editor` | ✗ | 用 `overlay.header` | ✗ | ✗ | ✗ | 用 `overlay.body` | 用 `overlay.action-bar` |
| `settings-list` | ✓ | ✓ | ✓ | ✗ | ✗ | ✓ | ✗ |

矩阵的作用是**一次性了结**「为什么这屏有/没有那个东西」的反复争论。想让某屏破例，走 §9。

### `detail` 和 `editor`：结构像，语义不同

这两个最容易混，都是「一个对象 + 一条动作栏」。四点区别：

| | `detail` | `editor` |
|---|---|---|
| 内容性质 | 只读呈现，可下钻到关联对象 | 可编辑输入，不可下钻 |
| 会不会清空 | 对象被删则整屏退出 | 提交或取消后必然消失，本来就不常驻 |
| 动作区性质 | 作用于已存在的对象（删除、进入编辑） | 提交一个尚未生效的变更 |
| 完成后去哪 | 停在原地，或对象被删则 pop | 关闭 overlay，回到打开它的那一屏、那个滚动位置 |

**判别口诀**：需要「保存/取消」语义的是 `editor`，走 overlay；不需要的是 `detail`，走导航栈。

### 正交覆盖层（overlay）

- **覆盖什么**：整屏，包括 `tab-bar`。
- **怎么触发**：只能由 `tab-bar` 的动作槽触发，或由 `detail` 页型 `screen.action-bar` 上的「编辑」触发。其它入口一律走 §9。
- **怎么关闭、怎么恢复**：完成或取消后关闭，下面那屏的滚动位置、筛选状态原样恢复。有未提交输入时关闭必须先确认。
- **能不能叠**：**不能。** overlay 内不得再开 overlay；overlay 内**可以**开恰好一个 sheet（如选分类）。叠 overlay 会让返回手势的语义无法确定，用户不知道退一步退到哪。
- **什么够格被提升进来**：一个会创建或修改一等对象、且**不能让用户丢失当前位置**的多字段流程。只读的东西不够格——只读走 `detail`。

### 底部弹层（sheet）

- **只做一件事**：选一个值，选完立刻返回调用方。
- **禁止**：多步流程（那是 `editor`）、导航到第三屏、叠第二层 sheet。
- 单选 sheet 选中即关闭，不要确认按钮；只有多选才出现 `sheet.action-bar`。

## §5 详情承载（桌面端「聚焦槽」在移动端的等价物）

移动端没有常驻的第二列，**不要移植侧栏模型**。等价机制是**下钻一层**（`detail` 页型）和**底部弹层**（sheet）。本章约束的是：什么够格拥有一个 `detail` 屏。

### 类型枚举

| 类型 | 承载对象 | 初始切面段 | 组合名 |
|---|---|---|---|
| `detail:transaction` | 交易 | identity + attributes | 轻详情 |
| `detail:budget` | 预算 | identity + attributes + related（该预算下的流水） | 关联详情 |
| `detail:category` | 分类 | identity + attributes + related（该分类下的流水） | 关联详情 |
| `detail:ledger` | 账本 | identity + attributes | 轻详情 |

### 准入规则

只有**枚举内一等对象的一个切面**才能进 `detail`。一等对象三条测试：① 有自己的身份，能被引用 ② 能被单独打开 ③ 生命周期超出一次会话。

**典型的不够格者，以及它们该去哪：**

| 不够格的东西 | 为什么 | 去哪 |
|---|---|---|
| 「月度统计」 | 是视图不是对象，没有身份 | `tab-root` 页型 |
| 「本月」 | 是时间范围 | `screen.filter-bar` |
| 「同步中」「已超支」 | 是**过程状态**，是对象的状态不是对象 | 状态显示在对象自己的区域里 |
| 「设置」 | 是配置层 | `settings-list` 页型 |

**明确写下：过程状态不是对象。** 不写这条，枚举会随着每一个流程步骤膨胀。

### 内部结构：所有类型共用一套段，每段可选

| 段 | 放什么 |
|---|---|
| `identity` | 这是什么、多少钱、当前进度 |
| `attributes` | 字段明细（日期、账本、备注、分类） |
| `related` | 关联的其它一等对象的列表 |
| `history` | 变更时间线 |

**三个组合名**（后面所有讨论都用这三个名字）：

- **轻详情** = identity + attributes
- **关联详情** = identity + attributes + related
- **全详情** = identity + attributes + related + history

### 新增类型的门槛

必须过一等对象三条测试，并在 §9 的区域申请里逐条回答。**过程状态不算对象**。

### 切换与返回

- 谁决定看哪个：**用户最后一次明确的点击**。系统不得自己把用户顶到另一个对象上。
- 代价：一步（点条目进，返回出）。
- 自足性：每个 `detail` 屏必须自带上下文（哪个账本、哪个月），不能依赖上一屏还在。
- 因为系统不抢焦点，**必须有补偿信号**：需要用户注意的事（预算超支）以状态点出现在 `tab-bar`，见 §7。不给补偿就等于静默丢事情。

### 返回键语义（分层，必须集中实现）

Android 硬件返回键和 iOS 返回手势共用同一套语义，**在一个中央处理器里实现，不要每屏各写一遍**——各写一遍必然出现某屏漏处理，用户一键退出 app：

1. 有 sheet 打开 → 关 sheet
2. 否则有 overlay 打开 → 有未提交输入先确认，否则关 overlay
3. 否则栈里有上一屏 → pop
4. 否则不在第一个 tab → 回第一个 tab
5. 否则 → 交给系统（Android 退到桌面）

## §6 主区域内容分流

| 内容 | 去处 | 形式 | 为什么 |
|---|---|---|---|
| 一笔交易 | `screen.body` 的列表 | 单行条目，点击 push `detail:transaction` | 高频浏览，需要密度 |
| 聚合数字（本期支出/收入/结余） | `screen.summary` | 定高非滚动，最多 3 个 | 滚动时不能丢，但也不能占太多高度 |
| 图表、分类占比、预算进度列表 | `screen.body` | 卡片 | 高度随数据变，进不了定高的 summary |
| 视图范围控件（时间、筛选、排序、搜索） | `screen.filter-bar` | 单行 | 它改变的是「在看什么」，不是内容本身 |
| 数据可信度提示（同步失败、离线） | `screen.notice` | 常驻单行 + 重试 | 会消失的提示等于没提示，见 §8 |
| 作用于某个对象的动作 | `screen.action-bar` / `overlay.action-bar` | 按钮 | 见下 |

**兜底**：不属于以上任何一类，就是停，走 §9。不要发明第 7 种形式。

### 动作只有一个宿主

**流水条目里不放可见按钮。** 要编辑或删除一笔，进 `detail:transaction`，动作在 `screen.action-bar`。

- **得到什么**：「动作只有一处」变成一个**结构事实**——流水列表里根本没有按钮可按，列表保持均匀、可快速扫读，条目高度一致。
- **失去什么**：多一次点击。
- **怎么补回来**：流水条目上必须显示足够的信息（金额、分类、备注、日期），让用户在绝大多数情况下**不需要**打开就能确认。这是买回失去那次点击的对价，不是可选项。
- **不给「轻量操作」开例外。** 「多轻算轻」是模糊线，agent 会各自发明一个阈值，然后列表里又长满按钮。

**唯一的例外是手势层，且已经枚举完毕**：列表条目允许**左滑删除**，恰好这一个，且必须二次确认。理由是手势不占视觉重量、不破坏「列表均匀可扫读」这条规则本身——而这条规则的真正目的就是均匀可扫读。**手势不得渲染成常驻可见按钮**，一旦常驻就回到了被禁止的形态。新增第二个手势动作要走 §9。

## §7 导航准入

### 分段

用三条属性测每一个候选项，不要套现成分类法：

| 项 | 会清空到零吗 | 点它是「发生一件事」还是「去一个地方」 | 永不清空吗 | 判定 |
|---|---|---|---|---|
| 明细 | 否 | 去一个地方 | 是 | **库** |
| 统计 | 否 | 去一个地方 | 是 | **库** |
| 预算 | 否 | 去一个地方 | 是 | **库** |
| 记一笔 | — | **发生一件事** | — | **动作** |
| 设置 | 否 | 去一个地方 | 是 | 三条全不满足「值得占导航位」→ **不进导航** |

**结果**：`tab-bar` = 3 个库 tab（明细 / 统计 / 预算）+ 1 个动作槽（记一笔）。设置进配置层，入口在明细屏的 `screen.header`。

**队列段目前为空。** 本产品当前没有会清空到零的收件箱类内容。将来若出现（例如「待确认的自动导入账单」），它是队列，**需要**数字计数徽标，并且必须走 §9 才能进导航。

### 每段的徽标规则

| 段 | 徽标 | 放错段的后果（具体会发生什么） |
|---|---|---|
| 库 | **禁止数字徽标**；允许状态点（如预算超支） | 库永不清空到零，数字就永远消不掉。用户两周内学会忽略所有徽标，真正要紧的预算超支也一起被忽略 |
| 动作 | 无徽标 | 把动作做成 tab 页的话，记完一笔用户停在「记一笔」页上，看不见刚记那笔落到哪，每次都要手动切回明细 |
| 队列（当前为空） | 必须数字计数 | 队列没有计数，用户不知道有几件事待办，只能靠反复点进去看 |
| 不进导航的（设置） | — | 放进导航就是拿 1/4 最值钱的位置给一个月开一次的东西，且它会变成所有「暂时不知道放哪」的东西的垃圾抽屉 |

### 上限

- **库 tab 上限 4**，当前用了 3。动作槽**恰好 1**，已被记一笔占满。
- 上限的作用是**逼出一个合并决策**，不是数字洁癖。
- **到上限后来了第 5 个怎么办**：不新增。二选一——① 合并两个现有库 tab；② 把其中一个降级为从另一个 tab 下钻。**由 owner 决定，并记一条 `docs/ui-contract/adr/layout/` 下的决策记录**（记下为什么是这两个合并、什么条件下重新考虑）。
- **动作槽已满时又来一个全局动作怎么办**：不加第 2 个动作槽。走 §9 提申请，默认答案是它进 `settings-list` 的一个「数据」子页并在那里成为一个动作项——但这需要 §9 批准，**不是决策树的兜底**。

## §8 非常态落位

只写规则，不画页面。

| 状态 | 去哪 | 怎么呈现 | **禁止** |
|---|---|---|---|
| 空 | 拥有该数据的区域内部，通常 `screen.body` | 一句「为什么空」+ 一个下一步动作 | 做成整屏插图**并把 `screen.filter-bar` 藏起来**——用户筛出空结果时会以为数据丢了，而不是筛错了。这是本项最常见的错误 |
| 加载（首次） | `screen.body` 内 | 骨架，形状与真实内容一致 | 全屏 spinner 覆盖（会让 header 和 filter-bar 不可用，用户退不出去也改不了筛选） |
| 加载（已有数据刷新） | `screen.body` 顶部 | 细进度条，**不替换已有内容** | 把已有内容换成骨架——用户会以为数据没了 |
| 局部失败 | `screen.notice` | 常驻一行 + 一个重试；内容区继续显示本地已有数据 | 用 toast——它会消失，之后用户不知道眼前的数字不可信 |
| 整屏失败 | `screen.body` 内的失败态 + 重试 | `screen.header` **必须保留**，否则用户退不出去 | 把 app 顶到一个全局错误屏 |

### 特殊情况 → 去处

| 特殊情况 | 去处 |
|---|---|
| 业务级校验失败（金额格式不对） | 就地在该字段下方；`overlay.action-bar` 的提交按钮**保持可点**——禁用按钮不告诉用户错在哪，点一下才能把错误暴露出来 |
| 需要人工介入（账本数据损坏） | `screen.notice` 常驻，指向 `settings-list` 下的修复页 |
| 成功确认（记一笔完成） | 关闭 overlay + 在 `screen.body` 顶部把新条目高亮一次。**不叠 toast**——动作的结果应该在结果所在的地方可见 |

### 新增页型时填这张空表

| 状态 | 去哪 | 怎么呈现 | 禁止 |
|---|---|---|---|
| 空 | | | |
| 加载（首次） | | | |
| 加载（刷新） | | | |
| 局部失败 | | | |
| 整屏失败 | | | |

## §9 变更流程

### 落位成功

直接实现。**不需要**改本文档。

### 落位失败（走到了「停」）

提一份**区域申请**，回答固定的五个问题：

1. 这是哪个一等对象的哪个切面？（不属于任何对象，就说明它是全局动作，直接看第 4 问）
2. 为什么现有区域装不下？逐个说明 `screen.body` / `screen.summary` / `sheet.body` / `settings-list` 各自为什么不行。
3. 它会清空到零吗？（决定它是队列还是库，见 §7）
4. 它需要多少高度？能不能在折叠后仍然可用？
5. 如果不给新区域，最接近的折中方案是什么？

**答不上来就说明需求本身没想清楚，那不是布局问题。** 先把需求想清楚再回来。

### 新增 `detail` 类型的门槛

过 §5 一等对象三条测试，三条都要在申请里逐条回答。

### 白名单怎么保持同步

**顺序固定：§2 白名单 → `src/ui-contract/regions.ts` 的 `RegionId` 类型 → 代码。不可反向。**

反向做（先写代码再补文档）的结果是文档变成对代码的描述，而不是对代码的约束——那时这份文档就失去全部作用了。

**文档和代码不一致时，改代码。**

### 推翻旧结论

不要删。搬到附录 B，写清楚「原本是什么 / 变成什么 / 为什么推翻」。同时在 `docs/ui-contract/adr/layout/` 记一条决策记录，写明什么条件下应该重新考虑。

## §10 反模式

| 不要 | 因为 | 改成 |
|---|---|---|
| 给库 tab 加数字徽标 | 库永不清空，数字永远消不掉，用户很快学会忽略全部徽标，连预算超支也一起忽略 | 用状态点表示「这里有情况」，具体数字放进那一屏的 `screen.summary` |
| 把「记一笔」做成第 4 个 tab 页 | 记完一笔后用户停在那一页上，看不到刚记的那笔落在哪，每次都得手动切回明细 | 做成 `tab-bar` 的动作槽，打开 `editor` overlay，完成后回到原处 |
| 把暂时不知道放哪的东西「先放设置里」 | 设置会在半年内变成一个无限下滚的垃圾抽屉，而且没人再敢删里面的东西 | 走 §1 到「停」，提 §9 申请。**接受「暂时没有地方放」这个结论** |
| 在流水条目里放编辑/删除按钮 | 条目高度不再一致，列表失去可扫读性；两三条就占满一屏，回看变慢 | 进 `detail:transaction` 操作；条目上显示足够信息以免打开 |
| 在 `screen.summary` 里放图表或可展开内容 | 它定高非滚动，高度会变的东西会把下面的列表挤掉或者被裁切 | 放 `screen.body` 的卡片里 |
| 一屏里建第二个滚动容器 | 嵌套滚动在 RN 上手势冲突，用户滑不动或者滑错层 | 整屏一个 `screen.body`，内部用分段而不是嵌套滚动 |
| overlay 上再叠 overlay | 返回手势的语义无法确定，用户不知道退一步退到哪 | 一层 overlay + 最多一个 sheet；更复杂的流程做成 overlay 内的分步 |
| 用 toast 报告数据失败 | toast 会消失，之后用户看着不可信的数字却不知道它不可信 | 常驻 `screen.notice` + 重试 |
| 用视口断点做降级 | 断点不知道 filter-bar 有没有已经折叠，会做多余的折叠 | 用「`screen.body` 装不下 3 个条目」这个真实测量的阈值 |
| 每屏各写一遍返回键处理 | 必然有某屏漏处理，用户一键退出 app | §5 那套分层语义，集中实现一次 |
| 在屏里画一个假的 `tab-bar` | 出现两个真相源，返回时闪烁 | `tab-bar` 属于 app 层，由导航器控制显隐 |
| 承诺「位置稳定、肌肉记忆有效」然后又做自动重排 | 承诺做不到就是骗用户 | 只承诺做得到的：tab 顺序固定不变；列表排序会随筛选变，且必须在 `screen.filter-bar` 上显示当前排序 |

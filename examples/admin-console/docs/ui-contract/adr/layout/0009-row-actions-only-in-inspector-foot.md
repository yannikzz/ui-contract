# 0009 单行操作只在 `inspector.foot`，表格禁止行尾操作列

| | |
|---|---|
| 状态 | 接受 |
| 日期 | 2026-08-20 |
| 相关条款 | `layout.md` §6.2、§6.3、§10 |
| 强制手段 | `TableColumnKind` 联合类型里**没有** `actions` 成员——写不出来，不靠人记 |
| 取代 | — |

## 背景

后台表格的单行操作（编辑 / 删除 / 停用……）有两个可能的宿主：表格的行尾操作列，或属性面板底部。行尾操作列是这类系统的默认做法。

## 决策

只放 `inspector.foot`。表格**禁止**行尾操作列，列型枚举里刻意不含 `actions`。

## 排除的备选

**表格行尾加操作列 / 「更多」菜单。** 它换来的是删一行只要一次点击。排除的理由是行尾操作列是无底洞：今天两个图标，半年后六个图标加一个「更多」，而列宽一直在和真正的数据列抢。更糟的是它制造了**两个操作宿主**——同一个「删除」在表格和面板各有一份，两边的确认逻辑、权限判断、乐观更新会各自演化，最终漂开。

禁掉之后「操作只有一个宿主」是结构事实：表格里根本没有按钮可按。这一条是整份规范里最容易被违反、也最值得守住的。

## 明知接受的代价

- 删一行要多一次点击：点行 → 面板 → 删除。**这是真代价，不是理论代价**
- 高频单行操作场景（例如审核流一天点几百次）会被这条明显拖慢

## 复议条件

- 出现一个**高频**单行操作，实测每天数百次量级，且多出的那次点击造成了可测量的工时损失——那时的正确做法是为该操作设计一个批量入口（`main.bulkbar`）或键盘快捷路径，**而不是**打开行尾操作列这个口子

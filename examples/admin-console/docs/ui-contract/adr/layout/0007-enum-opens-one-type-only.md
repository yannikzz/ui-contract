## 背景

[0006](0006-inspector-single-slot-enum.md) 定下有限类型枚举之后，枚举里现在填几型是一个独立的问题。设计稿只覆盖了表格行点开的那个对象；「系统」组下的用户 / 角色 / 权限点开时该显示什么，没有依据。

## 决策

只开 `content-item` 一型。其余留空，等本产品的一等对象被指认出来再补。

## 排除的备选

**按后台系统的常见形态预填用户 / 角色 / 权限三型。** 它换来的是「系统」组下的页面立刻有面板可用，不必等。排除的理由是这三型不是从本产品推出来的，是从**参考产品和模型记忆**里来的。枚举一旦写进规范就成了权威，后来的人会照着实现，而没有人会回头问「我们真的有『角色』这个一等对象吗」。

发明产品里不存在的对象，比留空的代价大：留空是一个可见的缺口，会被人问；预填是一个不可见的错误，不会。

## 明知接受的代价

「系统」组下的用户 / 角色页面点开时，面板无据可依——这些页面暂时只能用 P3 设置表单页型，没有属性面板。

## 复议条件

- 产品指认出第二个一等对象（通过 §5.4 三条判据）——那时按 §5.4 门槛新增第 2 型，**不要**复用 `content-item` 硬塞

## 背景：换肤预览在这个产品上几乎什么都没显示

ADR-0006（插件侧）为线框争取换肤预览，理由是「**只有线框能展示这个产品真实 IA
穿上这套皮的样子**」。装上之后实际看到的是：一个主按钮变色、一行导航底色变了，其余不动。

原因是结构性的，不是配色调得不好：**线框的 `Badge` 不知道自己是哪一种状态。**
六个状态标签渲染成同一个中性 chip，而在后台系统里，状态列的颜色正是视觉里最活的那部分。

所以预览展示的是穿上**一部分**皮的样子——表面、文字、品牌色。语义色永远看不到。

## 为什么不能让线框自己上色

需要一张「待审核 → 警告色」的映射表。**这张表当时在两份规范里都不存在**：
`design.md` 枚举了语义色能出现在哪些地方，没说本产品的六个状态各自对应哪一个。

线框自己编一张 = 第二个权威源，正是整套拆分要防的事。

## 决策：切成三层，按原来那条切线

判据没有变，还是「**换一套品牌视觉时会不会变**」：

| 层 | 内容 | 为什么在这一层 |
|---|---|---|
| `layout.md` §6.4 + `StatusKind` | 五个语义类，以及六个状态各归哪一类 | 「待审核需要有人动手」换皮肤不会变 |
| `design.md` §2.3b | 每个语义类用哪个 token | 换皮肤会变 |
| 线框 | 只接收类，不接收颜色 | 它一个颜色都没决定过 |

`Record<Status, StatusKind>` 是穷尽的，所以**加一个状态就必须给它归类**，忘了会类型报错。
`src/ui-contract.assert.ts` 另有一条：第六个语义类写不出来。

## 一个归类值得单独说

**已归档 → `neutral`，刻意不归 `done`。** 两者都是终态，但 `done` 是成功。
归档一份被驳回三次最后放弃的稿子，读起来不该像达成了什么。

`attention` 与 `blocked` 也刻意分开：用户动作不同——一个是去做，一个是得先解决别的。
把这两个合成一类是最常见的偷懒，合完之后状态列就只剩「有事」和「没事」两档。

## 排除的方案

| 方案 | 为什么不 |
|---|---|
| 线框保持全灰 | 那么换肤预览在这个产品上回答不了什么，而它是 ADR-0006 花很大力气争取来的能力 |
| 映射表放 `design.md` | 「待审核算不算需要注意」换皮肤不会变，按切线它不归视觉 |
| 映射表放线框 | 线框是一次性的，且它会成为第二个权威源 |
| 直接把状态字符串映到颜色，不要中间的类 | 六个状态映六个颜色，等于没有分类。加第七个状态时没有任何东西逼你想清楚它属于哪一类 |
| 类的数量放开 | 封闭集才有「加一类要走 §9」这件事。五类覆盖不了通常说明状态本身没想清楚 |

## 代价

- **线框多知道了一件事。** 它原来只知道「这里有个状态标签」，现在还知道「这是哪一类」。
  这是真的多了一层耦合——换来的是预览能回答问题。
- **加一个状态的成本变高了**：要归类，而归类要想清楚它是 attention 还是 blocked。
  这是刻意的成本，不是副作用。
- **未换肤时看不出这一层做了什么**——五个类仍然是同一个灰。这是对的：
  线框默认不表达颜色语义，只有读了 token 文件才表达。

## 复议条件

| 条件 | 动作 |
|---|---|
| 出现一个五类都装不下的状态 | 先怀疑那个状态本身，再考虑加类；加类走 `layout.md` §9 |
| 语义色的使用面积开始超出 §2.3 硬规则 2（小标签 / 状态点 / 浅底提示条） | 说明有人在用它做装饰，回到 §1.2 第二条 |

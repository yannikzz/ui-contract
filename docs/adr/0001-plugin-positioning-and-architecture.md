## 背景

v0.1.0 是单体技能，能跑通，但两件事没有明确答案，导致 issue #1 无法评审：

1. **这个 plugin 到底管到哪**——上游到产品定位吗？下游到代码规范吗？边界不定，拆包必然拆歪
2. **产物是文档还是代码资产**——现有线框是一次性参考实现，但用户实际要的是「token 和组件代码长期被维护」，这两者对包的切法要求不同

在没有 1、2 的答案之前，issue #1 里的 12 个包只是对现状的重排，不是对目标的分解。

---

## 决策

### 一、定位

> **在 Coding Agent 开发前端的场景下，负责「地基层」：在 agent 写第一行业务界面代码之前，把结构、视觉、落位规则定义成 agent 绕不过去的形式，并让它随代码一起长期存活。**

三个限定词都是排他的：

| 限定 | 在范围内 | 排除 |
|---|---|---|
| **面向 Coding Agent** | 所有取舍以「agent 会怎么误读」为准 | 人类团队协作的沟通载体（Figma / Storybook 的地盘） |
| **前端界面环节** | 功能清单 → 界面结构 → 视觉 → 约束 | 上游：产品定位、功能取舍<br>下游：业务逻辑、泛化代码规范 |
| **长期存活** | 三个月后仍在起作用 | 一次性生成的漂亮文档 |

两条使用场景是同一件事的两种入口，共用下游单元：

| | 治熵（已有项目） | 0-1（立项） |
|---|---|---|
| 状态 | 地基已被踩烂 | 地基未浇 |
| 动作 | 重浇一遍并加钢筋 | 一次浇对并加钢筋 |
| 差别 | 跑 `baseline` 逆向实际区域树 | 功能清单已定，直接进 `layout` |

**「加钢筋」是同一件事**——这是两条起点能共用 `layout` / `design` / `assets` / `wireframe` / `enforce` / `audit` 的根据。

**0-1 线的上游边界钉死在「产品定位与功能框架已讨论清楚」**。本 plugin 不做产品发现、不做功能取舍。输入是功能清单，不是产品想法。

### 二、六条原则

后续所有能力设计与 issue 评审以此为判据。

**1. 产物必须 agent 可执行，不只是人可读。**
优先级 `类型 > 结构化产物（决策树 / 白名单 / token 文件） > 散文文档`。
→ 判据：任何新增能力先问「它最终落成哪种形式的约束」。落不到可判定形式的，定位必须是「只解释、不约束」。

**2. 一条切线，不许发明新维度。**
换皮会变 → 视觉；不变 → 结构。这是原子公理，所有归属问题用它判。
→ 注意：**冻结度是正交维度，不是第二条切线**。它回答「这条有多硬」，不回答「它归谁」，因此不违反本条。

**3. 不生产用户的答案，只生产用户的决策。**
→ 判据：所有加速手段（默认值、模板、可视化、赶时间模式）都与本条对冲。可以加速，但必须**成组给选项 + 每项标代价**，不能给单一默认值让用户盖章。

**4. 只管「由结构推导得出」的东西。**
判据是切线的同构版：能不能从 `layout.md §2` / 切线推导出来？

| 事项 | 在否 | 依据 |
|---|---|---|
| token | ✅ | 视觉规范的直接产物 |
| 布局框架 | ✅ | 区域树的直接产物 |
| 组件代码 | ⚠️ 部分 | 结构性组件（Shell / Region / Slot）在；业务组件不在 |
| 命名风格 / 状态管理 / 错误处理 | ❌ | 推导不出来，是别人的地盘 |

**5. 约束必须能随代码活下去，否则不算交付。**
文档会腐烂，类型不会。三层强制中只有编译期层是自维护的。
→ 判据：持续把规则往类型层下沉；且必须有能力验证「三个月后是否仍在起作用」。

**6. 任何时候都能从中间进入。**
根本原因不是用户懒，是**地基是长期资产而对话是短期的**。
→ 判据：任何包若依赖「上一步的会话上下文」而非磁盘产物，设计即为错。

### 三、三个具体决定

#### 决定 A — token 与布局框架是**生产资产**，线框是它的低保真消费者（分层）

| | 资产层 | 展示层 |
|---|---|---|
| 住哪 | 项目生产目录，跟随项目既有技术栈 | 独立小工程 |
| 内容 | token 文件、Shell / Region / Slot 结构组件、`RegionId` 类型 | 低保真线框 + 标注层 |
| 生命 | 长期维护，随业务演进 | 一次性，结构变了重生成 |
| 品牌 | **带** | **强制覆盖为中性值** |

**排除的方案：**

- **A′ 全一次性**（token 只是文档里的文字，生产代码另写）——规范与代码之间留一道人肉翻译，漂移必然发生，且违反原则 5
- **A″ 全生产**（线框即生产壳）——「线框不带品牌视觉」当场自相矛盾，线框会重新成为第二视觉权威源

**两条连带推论（重要，非叠加）：**

1. **`design.md` 从「存值」变为「存规则」。** token 文件是代码里唯一的值权威，`design.md` 不得再出现色值 / 尺寸值，一律写「见 token 文件」。这与 `layout.md` 早已不存视觉值是同构的——切线未变，只是多了一跳。
2. **「线框不带品牌视觉」的理由升级**：从**藏起来**变为**藏起来 + 指路**。agent 抄线框只抄得到结构；它需要品牌视觉时，唯一去处是 token 文件。比原方案严密。

**代价：** 资产层是生产代码，会被业务需求推着改（有人赶需求在 Shell 里加 slot 而规范没跟）。**分层引入了一个新的漂移面**——这是决定 C 的直接理由，而非锦上添花。

#### 决定 B — 0-1 线生成品牌视觉

第 3 步动词分叉，**但不拆包**（两分支产出同一份产物、判据相同，属同一进入点的两个分支）：

```
有视觉规范 / token  → align      对齐边界、搬走结构内容、统一区域名
无视觉规范          → originate  生成品牌 → 落成 token 文件
```

**`originate` 必须把选择给在「品牌属性维度」上，不是配色方案。** 用户对「蓝还是绿」没有判断力，对「专业可靠还是轻松亲和」有。给 3 个互斥的属性组合（密度 ↔ 呼吸感、克制 ↔ 表现力、锐利 ↔ 柔和…），每个标代价，用户选定后才推导具体色值与尺度。顺序反了就是让用户给 agent 的答案盖章，违反原则 3。

**复用而非自造**：`originate` 调用现有的 `frontend-design` 技能。品牌生成是本 plugin 唯一需要产生审美的地方，也是最容易退化成「又一套 Tailwind 默认蓝」的地方。

**冻结度的首个应用点**：0-1 生成的品牌是假设不是事实，默认标 🌡 试行（「首次真实用户反馈后复议」）。结构条款推翻代价大所以冻结，品牌本来就是设计了要换的——**切线在此再次生效**。

**排除的方案：**

- **不生成品牌**（要求用户自带视觉规范）——0-1 线当场断掉，而这是两大场景之一
- **生成一套默认品牌**——违反原则 3，且 SKILL.md 已写明「用户会接受默认值，那份规范就不再是他的了」

#### 决定 C — 增加「体检」能力

输入是磁盘产物（原则 6），输出是**差异报告 + 修复建议**，**不自动修**。

**设计原则：体检的价值与其运行成本成反比。** 必须便宜到能每个大版本跑、甚至进 CI，因此**主体是全自动检查，agent 判断只作补充**：

| 检查项 | 手段 | 自动化 |
|---|---|---|
| 代码中区域名 ⊆ 白名单 | 类型检查 + grep `data-region` | 全自动 |
| `as any` / 字面量绕过 `RegionId` | grep | 全自动 |
| 代码中硬编码色值（绕过 token） | 正则 | 全自动 |
| `design.md` 残留硬值（违反决定 A 推论 1） | 正则 | 全自动 |
| 白名单每行有「禁止放」 | 解析表格 | 全自动 |
| 资产层 Shell / slot 与 `layout.md` 区域树一致 | 结构比对 | 全自动 |
| 决策树对最近 N 个新功能是否仍为全函数 | 拿真实 commit 走树 | agent |
| 区域描述是「放什么」而非「是什么」 | 语义判断 | agent |

前六项覆盖约八成且可进 CI。

**这是本 plugin 唯一能自证有效的地方。** eval 只能验产物形态（有无决策树、有无禁止列），验不了「三个月后结构还在」——而后者才是承诺。体检跑几个季度后能产出「agent 撞停 N 次、区域名零违规」的真实数据。

**排除的方案：**

- **不做体检**——原则 5 落空，分层引入的新漂移面无人看管
- **体检自动修复**——修复即改结构，绕过了决策树本身；且违反「文档先改代码后跟」

#### 决定 D — 两个 ADR 目录的分工

| 目录 | 记什么 | 谁在读 |
|---|---|---|
| `docs/adr/`（本仓库） | **开发和优化本 plugin 的决策**——定位、原则、包边界、实施顺序 | 本仓库的开发者 |
| `docs/ui-contract/adr/{layout,design}/` | **plugin 产出到使用者生产项目里的决策**——那个项目的结构决策与视觉决策 | 使用者项目的开发者与 agent |

两者是不同产品的决策，不是同一序列的两段。

**由此定：资产层（token 文件、Shell / Region / Slot 结构组件、`RegionId`）的实现决策，按切线判归 `adr/layout/` 或 `adr/design/`。**
理由：资产层是两份规范的代码化，其决策都能追溯到某条条款——**不引入新维度，符合原则 2**。

**排除的方案：** 归 `docs/adr/`。它会把使用者项目的决策混进本 plugin 的开发决策里，且要修改 issue #1 已定的「`setup` 探查到 `docs/adr/` 时不并入」那条规则；选本方案则无需改动任何既有规则。

#### 决定 E — 重构与扩展分成两个 issue，但按 14 包边界切

issue #1 的验收线是「现有 4 个 eval 每步全过」，**这是「行为不变」的验收，只对重构有效**。新能力（`assets` 生产化、`originate`、`audit`）无法这样验收，混在一起则无法判断失败原因。

| | 范围 | 验收线 | 版本 |
|---|---|---|---|
| **issue #1** | 拆包重构，**但按 14 包边界切**：`assets` 包建出来，内容是现有 `wire.tsx.template` 平移的最小版；`wireframe` 直接只写展示层 | 现有 4 eval 全过 | 0.2.0 |
| **issue #2** | `originate`、`audit` 全自动检查、冻结度、资产层多技术栈适配 | 新增 eval | 0.3.0 |

**排除的方案：**

- **合成一个 issue**——验收线失效
- **#1 按 12 包切、#2 再掏空**——`wireframe` 包写两遍

#### 决定 F — `audit` 提到第 0 步，独立于拆包发布

`audit` 只读磁盘产物，不依赖拆包，是纯增量。早期只能检文档层 + `RegionId` union（资产层尚不存在），但这对 v0.1.0 现有用户已立刻有价值——「你三个月前生成的规范还在起作用吗」。

它同时是**门槛最低的入口**：用户不必先跑完整流程就能用。这与拆包的商业理由一致（把一次性大额投入变成可分期）。

**新产物类别**：`audit` 产出的是**可执行脚本**——装进用户仓库、能进 CI、脱离 agent 独立运行。现有 12 包全是 markdown，`install.sh` 与两份 manifest 都未考虑过非 markdown 产物，根 `CLAUDE.md` 要记的同步点因此从 3 个变 4 个。

## 后果

### 骨架

```
原语层   decision-interview · spec-before-code · decision-record · constraint-by-types
词汇层   ui-contract-glossary
事实层   ui-contract-setup ─┬─ baseline    已有项目：逆向出实际区域树
                            └─ (0-1：功能清单已定，直接进 layout)
能力层   ui-contract-layout      结构           → layout.md
         ui-contract-design      align│originate → design.md（只存规则）+ token 文件
         ui-contract-assets      资产层：token / 结构组件 / RegionId → 进生产   ★新
         ui-contract-wireframe   展示层：消费资产、覆盖品牌、低保真
         ui-contract-enforce     三层拦截 + 资产边界
         ui-contract-audit       体检：差异报告，不自动修                       ★新
编排层   ui-contract
```

**包数 12 → 14。**

### 对 issue #1 的影响（待评审逐条落实）

| 影响 | 落在哪个 issue |
|---|---|
| 新增 2 包 | `ui-contract-assets`、`ui-contract-audit` |
| `design` 包动词分叉 | 现文案「align / slim down」只覆盖治熵线，缺 `originate` |
| `design.md` 定义变更 | 不再存值；随之需新增完工判据 |
| `wireframe` 包被掏走一半 | 资产层移出，该包只剩展示层 |
| 依赖图变更 | 原「扇形：三者共同依赖 `layout.md §2`」需重画——`wireframe` 改为依赖 `assets`，`enforce` 与 `audit` 依赖 `assets` + 白名单 |
| 完工判据 | 新增项（token 唯一权威、资产层与区域树一致、体检可跑）尚无所有者 |
| 五步实施顺序 | 需重新校验是否仍成立 |

### 新增的正交维度：冻结度

不属于切线，独立标注每条条款「现在有多硬」：

```
🔒 已冻结   来自事实       → 进 union type、进硬停
🌡 试行     来自假设       → 进文档不进类型，标注复议条件
✏ 待定     尚无结论       → 进「本规范不决定」附录
```

与 ADR 配套但非同一件事：**ADR 记「为什么」，冻结度记「这条现在有多硬」**。

## 复议条件

| 决策 | 什么条件下复议 |
|---|---|
| **原则 1**（类型 > 文档） | 若模型能力演进到可靠遵守自然语言约束，编译期层的必要性下降 |
| **决定 A**（分层） | 若资产层难以适配 React 之外的技术栈（Vue / Svelte / RN / 原生），退回 A′ 并承认人肉翻译 |
| **决定 B**（生成品牌） | 若实测生成品牌被用户推翻的比例过高，说明这个能力不该在本 plugin 内 |
| **决定 C**（体检） | 若全自动检查项的实际覆盖率显著低于八成，体检退化为 agent 主观复读，价值不成立 |
| **包数 14** | 若某包的 `SKILL.md` 长期不足 30 行，说明切早了，应并回上游包。**当前最接近这条线的是掏空后的 `wireframe`**——先观察，不预并 |
| **决定 D** | 若出现既非结构、也非视觉、又确属使用者项目的决策类别，说明切线不够用，届时才考虑第三个目录 |

单条原则若被单独推翻，**新立 ADR supersede 该条，不重写本文件**。

## 未决

- 资产层在 monorepo / 多端项目中的落位（一份 token 多端消费，还是各端各一份）

**已在 issue #2 内定案，此处存档：**

| 原未决项 | 定案 |
|---|---|
| `originate` 与 `frontend-design` 的调用边界 | `originate` + `decision-interview` 负责**逼出用户的选择**（成组给方向、标代价、一次一问）；`frontend-design` 负责**把选定方向变成好看的具体值** |
| 体检脚本的宿主形态 | 装进用户仓库（建议 `scripts/ui-contract-audit.*`），脱离 agent 独立运行；输出终端摘要 + 可选 markdown 报告；Node 项目走 npm script，非 Node 项目降级为 shell + grep |

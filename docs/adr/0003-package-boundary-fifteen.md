---

## 背景

ADR-0001 把包数定为 14。评审 issue #1 时查到一个**分类错误**：

单体 `SKILL.md` 的 §Language（「用用户说的语言写产物、一个概念一种译法、把选择记进术语表」）被划归 `ui-contract-glossary`。而 `glossary` 只被 3 个包调用（`layout` / `design` / 编排层）——于是 `wireframe`（写目录级 `CLAUDE.md` 与注解文案）、`setup`（写 `config.md`）、`baseline`（写 `as-built.md`）、`audit`（写差异报告）**都产出文字，却拿不到语言规则**。

§Language 里那半规则**不含任何 UI 词汇**。它被放进词汇层，不是因为它属于那里，而是因为它在单体里恰好和术语表写在同一节。

---

## 决策

> **§Language 里领域无关的那半抽成第 5 个原语；UI 专属的术语对照表留在 `ui-contract-glossary`。包数 14 → 15。**

判据是 ADR-0001 的三层结构本身：领域无关的纪律住原语层。新 `structure.sh` 的「原语层不含 UI 词汇」那条断言正好能守住这次归属——**分类错误可以被机械检出，这是它该住在原语层的旁证。**

---

## 排除的方案

**所有产出文件的包都调用 `glossary`。**
会让 `glossary` 被 9 个包调用，而它的主体（三件套分工 + 那条唯一的切分线）对 `setup` 和 `audit` 毫无用处。为一条四行的语言规则吊进整个词汇层，是纯上下文浪费——正是拆包要解决的问题之一。

**每个包内联一句「用用户的语言写」。**
一句话重复 5 遍就是 5 个漂移点。单体时代的内联标准是「低于 100 行才内联」，但那条标准衡量的是**长度**，这里的问题是**份数**。

---

## 对 ADR-0001 的 supersede

ADR-0001 有两处写着 14。**「后果 · 骨架」一节末尾的「包数 12 → 14」直接读作「12 → 15」，骨架图中原语层补上第 5 个；** 复议条件表中的这一行则要细说：

> **包数 14** — 若某包的 `SKILL.md` 长期不足 30 行，说明切早了，应并回上游包。**当前最接近这条线的是掏空后的 `wireframe`**——先观察，不预并

**该行的正文继续有效，只有两处更新：**

| | 原 | 现 |
|---|---|---|
| 基数 | 14 | **15** |
| 当前最接近该线的包 | 掏空后的 `wireframe` | **`spec-before-code`（30 行）与 `deliverable-language`（35 行）** |

**这一格是被实测改掉的，不是被推理改掉的。** 评审时预判最薄的是 `assets`——理由是它在 0.2.0 里只装 `RegionId` + `Region`，`Shell` / `Slot` 已推给 issue #2。写完实测：`assets` 55 行，排在中位；真正压在 30 行线上的是两个原语，而它们薄的原因完全不同——**原语薄是因为纪律本身就短，不是因为切早了**。

实测排序（`SKILL.md` 行数）：

```
30  spec-before-code          ← 正好在线上
35  deliverable-language
44  constraint-by-types
48  ui-contract-design
49  ui-contract-setup
50  decision-interview
53  ui-contract-wireframe
55  ui-contract-assets        ← 评审预判的最薄，实际在中位
…
106 ui-contract-glossary
```

由此得到一个原判据没有的区分：**"包太小"这条复议条件对原语层和能力层不是同一个意思。** 一条纪律用 30 行讲清楚是它写得好；一个能力包只有 30 行则通常意味着它没做完。复议时按层分别判，不要用同一个数字一刀切。

**这不是新的复议条件，是同一条复议条件的对象变了。** 记在这里是因为 ADR-0001 已 Accepted，纪律要求 supersede 而非改写。

## 连带影响

**description 常驻预算：~4400 → 实测 6415 字符**（上限 15×1024 = 15360）。三个来源：新增第 5 个原语、`audit` 破例配富触发词、包数本身。

评审时估的是 ~4900，实测高出约三成——每个窄 description 写下来是 400–500 字符，而不是估计的 ~300。数字记实测值，不记估计值：常驻预算是会被后续每一个包蚕食的东西，用一个偏低三成的基线去判断"还剩多少"会得出错误结论。

一个只在实测时才会暴露的约束：**上限同时是 1024 字符和 1022 UTF-8 字节**。中文每字 3 字节，所以带中文触发词的 description 会在字符数还合规时先撞字节上限（编排层实测 967 字符 / 1053 字节，超了）。压缩时**只删英文冗余，不删任何匹配真实用户说法的短语**——曾经为省字符删掉一条触发短语，而那条正好是一个真实测试 query。

「只有编排层配富触发词」这条硬规矩因 `audit` 的入口地位破了一次例，**现在要守住的是 13 个窄 description**——每一个只覆盖自己那一件产物。

## issue #1 推出去的清单

本节是 issue #1 评审的**硬性产物**：这些不是「以后可以做」，其中有一条是**已知缺陷**，忘记它等于带着一个明知的 bug 发版。

| # | 推出去的东西 | 性质 |
|---|---|---|
| 1 | `Shell` / `Slot` 结构组件 | 待建能力（现有模板中不存在，非平移） |
| 2 | token 文件；以及由此产生的断链——**0.2.0 的 `design.md` 会指向一个不存在的文件** | **已知缺陷**，靠「0.2.0 不公开」兜住 |
| 3 | `design` 的第二条完工判据（品牌属性选项成组给出且每项标代价） | 待建判据 |
| 4 | `originate` 分支（ADR-0001 决定 B） | 待建能力 |
| 5 | `audit` 全自动检查补齐（0.2.0 只有文档层 + `RegionId`） | 待建能力 |
| 6 | 冻结度（ADR-0001 新增的正交维度） | 待建机制 |
| 7 | 资产层多技术栈适配 | 待建能力 |
| 8 | 三项**待实测**：编排层与 `audit` 的触发词互抢 · 原语层与生态既有技能（`grilling` / `to-spec`）撞名 · 拿掉 `examples/` 后产出质量是否下降 | 缺证据，#2 的范围取决于结果 |

第 2 项与「0.2.0 不公开」是**绑定的一对**：动其中任何一个，另一个必须重判。

第 8 项之所以不现在写进 issue #2 的正文：它的答案依赖 #1 跑完之后的实测。这个仓库刚因为「从假象数据推结论」吃过亏（见 `tests/scenarios/FINDINGS.md` 的作废表），现在写就是猜。

## 复议条件

| 决策 | 什么条件下复议 |
|---|---|
| **第 5 个原语** | 实测 35 行。若它长期停在 30 行附近且内容与 `decision-interview` 反复交叉引用，说明抽得过细，应并回去 |
| **包数 15** | 同 ADR-0001 该行正文，基数与对象按上表更新 |
| **`audit` 破例配富触发词** | 若实测显示编排层与 `audit` 的触发面互抢显著，说明「两个入口」这个设想不成立，应退回单入口 + 编排层路由 |
| **description 常驻预算** | 若常驻合计超过上限的一半（约 7700 字符），说明窄 description 的纪律没守住，应逐包收窄而非提高预算 |
| **推出去的第 2 项** | 若 0.2.0 的公开时点提前，该缺陷立即从「可接受」变为「阻塞发布」 |
